## 2. The work in one paragraph, and the thesis

flasharray-eda is an open-source prototype (Apache 2.0, github.com/sdodsley/flasharray-eda) by Simon Dodsley of Everpure that turns a standalone Everpure FlashArray into an event source for Event-Driven Ansible with no Pure1, no Fusion and no monitoring stack. It grew out of a blog thought experiment pairing the Fusion MCP server with Event-Driven Ansible and that experiment's runnable follow-up; this project forked the follow-up and removed the Fusion dependency, because the array itself exposes a cursorable alert log, an attributable audit log and its own performance and capacity history over REST, and will push alerts and audits over syslog. It consists of two ansible-rulebook source plugins (purefa_events, an asyncio REST poller with six signals, and purefa_syslog, a UDP/TCP listener for the array's own syslog), ten rulebooks (alerts, change control, config drift, health, replication, capacity, performance, a composite anomaly rule, syslog, Alertmanager), fifteen playbooks that act through everpure.flasharray modules (the SDK is used only to read state the modules do not expose), a git-backed desired-state baseline, a Prometheus rules file for the array's native OpenMetrics exporter, and a decision environment definition. All five phases of the plan were built, with an exit test recorded for each phase, on 2026-10-20 against two lab arrays running Purity//FA 6.10.6 (REST 2.46), connected for replication, with ansible-rulebook 1.3.2, ansible-core 2.17, py-pure-client 1.94.1 and ansible.eda 2.13.0. The loop reverts an unsanctioned NTP change within one audit poll and names who made it, lights the identify LED on the controller that a replayed failure named, copies and size-verifies a replicated volume on the target array, caps a noisy-neighbour volume and lifts the cap when latency returns to normal, asks a human before freeing any space, and fires a composite rule that snapshots everything and lengthens the eradication delay when the first-hour signature of a ransomware event appears. Every remediation is gated by maintenance windows, a service-account check, per-site switches and literal throttles.

**Thesis (one sentence):** A FlashArray is already an event source: with nothing but an API token per array, a rulebook can revert, light, verify, cap, protect and ask, and the real design work is deciding which of those it may do without a human.

## 4. Key messages and their evidence

1. **The array is already an event source; no Pure1, Fusion or monitoring stack is required.** Evidence: the plan's verdict "A standalone FlashArray is a better EDA source than Fusion was"; the plan's eight-row table (section 6, table B) lists /alerts, /audits, /hardware, /arrays/space history, /arrays/performance history, replication endpoints, /maintenance-windows and the self-check endpoints, all REST 2.0 to 2.52; native push via syslog programs purity.alert / purity.audit / purity.test, SNMP trap/inform, and OpenMetrics on Purity//FA 6.7+. The pull path needs only an API token per array with a read-only role; the predecessor needed Fusion and this project forked it and removed that dependency.

2. **The audit log turns drift detection into change control.** Evidence: a second local user added an NTP server on array A; the audit arrived with that user's name and reconcile.yml reverted the list to the git baseline within one poll (audits polled every 10 s), log line "array A: <second local user> ran purearray setattr --ntpserver pool.ntp.org,time.google.com -> reverted to baseline", PLAY RECAP ok=5 changed=2 skipped=1 failed=0; the same user's purevol destroy and eradicate were each reported with user, interface and audit id (158607944, 158607945); a git push to the baseline repository applied NTP and DNS forward (array A ok=7 changed=2). Purity logs the change as `purearray setattr --ntpserver`; there is no purentp command.

3. **Transport is a deployment choice; the rules and the actions are the same for pull, push and the zero-custom-code path.** Evidence: the same identify_led.yml lit the LED on CT1 of a real array from a replayed health fixture (18:00) and from an Alertmanager webhook payload (18:19), PLAY RECAP ok=4 changed=2 both times; the syslog listener produced notifications from replayed purity.audit and purity.alert lines over UDP and TCP; the Alertmanager rulebook uses the stock ansible.eda.alertmanager source with no code of this project on the array side. Blog: "How events reach the rulebook is a deployment choice, not a design one."

4. **Deciding what may act on its own is most of the design work: three levels of oversight and four guard rails.** Evidence: only NTP and DNS are auto-reverted; LDAP, SafeMode/eradication and admin-auth settings are notify-only ("the setting exists to resist change"); anything that frees space needs an approval, and the array's refusal of a SafeMode-locked snapshot was reported, not forced; every remediation is suppressed inside a maintenance window (observed four times: the same NTP drift "not reconciled", bay CH0.BAY3 "not actioned", a replayed alert 42 "not routed", a health event stamped maintenance_active with the window's expiry); an automation_users list stops the automation reacting to itself (exercised for real when the shared account's own changes were logged, not reverted); three per-site switches fall back to notify; the plugin only issues GETs, so the polling token can carry a read-only role (design guidance; the lab used one shared write-capable token).

5. **Replication becomes an RPO contract and DR becomes a measurement.** Evidence: a paused replica link reported from both ends (recovery point 5 s old on the source view, 2061 s old on the target view); a replayed overdue event produced a real immediate replicated snapshot of the hourly protection group (changed=True); the DR drill on array B found the latest completed transfer from array A, copied one member volume out of it, verified its size, then destroyed and eradicated the copy (ok=8 changed=3 failed=0); a replayed degraded stretched pod moved the local hosts' preferred array to the online side and the recovery event moved it back.

6. **The composite rule gives SafeMode the one thing it cannot do: noticing.** Evidence: a multi-event `all` condition with a 15-minute timeout joining a data-reduction drop, a snapshot or write surge and a human destroying snapshots on the same array fired on the first replay on ansible-rulebook 1.3.2; the response took immediate snapshots of the protection groups with members, lengthened the enabled eradication delay from 1 to 2 days and wrote a critical record (ok=7 changed=3 ignored=1); the anomaly.yml header: "Nothing is shortened, destroyed or disabled."

7. **What did not survive contact with hardware was the useful part.** Evidence: eight Purity REST facts and five ansible-rulebook constraints documented; honest gaps named (no live syslog line yet, Prometheus rules not evaluated live, decision environment not built, AAP approval node unproven).

### Diagram F: the gates every remediation passes, with the lab proof for each

Draw as a horizontal pipeline, Event -> Gate 1 -> Gate 2 -> Gate 3 -> Throttle -> Action, with a "log or notify only" bypass lane under each gate, and a three-rung ladder beside it.

- **Gate 1, maintenance_active == false.** Stamped on the event by the plugin from one cached /maintenance-windows read per array; the sibling rule logs "not routed / not reconciled / not actioned" when true. Lab proof: a 3600 s window turned the same NTP drift from "reverted to baseline" into "not reconciled"; a replayed unhealthy bay CH0.BAY3 inside a window was "not actioned"; a replayed alert 42 inside a window was "not routed"; the health event carried the window's created and expires.
- **Gate 2, by_automation == false.** The automation_users list (example svc-eda) is the identity the remediation playbooks authenticate as; its audit records are logged, never reconciled; the syslog fast notification and the anomaly rule's audit leg require the same. Lab proof: a QA harness sharing the lab account logged puredns setattr, purevol tag and puresnmp setattr; with automation_users naming that account, change control logged them ("automation (<shared automation account>) on array A: puresnmp setattr localhost") and acted only on the second local user's changes.
- **Gate 3, per-site switch true.** qos_auto_cap, activecluster_auto_prefer, replication_auto_replicate_now; when false the same condition matches a notify-only sibling rule, "so a site can start with notify only".
- **Throttle.** Literal once_within grouped by array plus component, volume, pod or protection group: reconcile 2 min, QoS 10 min, identify LED 1 h, anomaly 1 h, capacity request 24 h.
- **Action.** A playbook on the inventory host named by the event's `array`; it appends a JSON record to the alert log.

The ladder, "three levels of oversight": rung 1 AUTO-REMEDIATE the boring settings (NTP, DNS: idempotent reapplies from the baseline); rung 2 NOTIFY ONLY, always, for anything that can lock an admin out or loosen SafeMode (directory services, which need the bind password; SafeMode and eradication config, "the setting exists to resist change"; admin authentication: lockout, login attempts, password length, SSO; and in the baseline README also SMTP, syslog, SNMP and alert watchers); rung 3 APPROVAL GATE for anything that frees space (request file -> human approval -> reclaim; SafeMode-locked objects refused by the array, never forced). Caption: "Deciding which is which is most of the design work." Credential note: the polling token has a read-only array role (the plugin only issues GETs); the playbooks use a write credential that should be the dedicated service account; both reach the code through environment variables, so no file in the tree holds a secret.

## 8. Lessons and gotchas worth a slide

**The three things (blog, verbatim):** "Three things I would tell anyone starting the same build. First, ansible-rulebook conditions allow no Jinja filters and no arithmetic, so the source plugin emits the booleans and counters the rules need. Second, anything a rulebook must remember across a restart belongs on the array or in a file, not in a fact. Third, use a dedicated service account: another automation was using the same user on the lab array during the run, and change control saw its changes exactly as it would see an operator's."

**Five ansible-rulebook constraints and the design answer to each (all hit in the build):**

| Constraint | Design answer |
|---|---|
| Conditions allow no Jinja filters (`\| length`) and no arithmetic (`lag_ms > rpo * 1000`) | the plugin emits the booleans and counters: drive_issue_count, hardware_issue_count, rpo_breached, rpo_breach_polls, paused_for_s, days_to_full_known, baseline_known, drr_drop, snapshot_surge, write_surge, eda_capped, high_latency_polls, normal_polls, iops_share_pct, overdue, stuck, recovered, by_automation, system_user, maintenance_active; list settings become sorted CSV strings so a rule compares with one `!=` |
| `throttle: once_within` must be a literal (validated against the schema before variable substitution) | cooldowns live in the rulebooks, not in vars (33 literals) |
| `run_playbook` copies only the playbook into a temporary project directory | included task files use absolute paths (set_dns_tasks, runbook_dir); everything the playbook needs arrives as extra_vars |
| `--vars` takes one file, `-e` means that file, and its values are not templated | replay tests build a single vars file with sed (REPLAY_ARRAY, REPLAY_COMPONENT and similar placeholders) |
| `localhost` must be declared in the inventory, because run_playbook is limited to the ruleset's `hosts: all` and the implicit localhost is not in `all` | inventory/example.yml declares it explicitly |

Also: ansible.eda must be on ANSIBLE_COLLECTIONS_PATH for the webhook, tick and generic sources (run.sh adds a collections/ directory beside the venv); Java 17+ must be on the path; replay rulebooks are copies of the production rules because ansible-rulebook has no include and swapping a source for an event stream is an EDA Controller feature. A positive: the multi-event `all` condition with `events.x <<` assignment, an `or` across two event types and `timeout: 15 minutes` parses and fires on 1.3.2; it fired on the first replay.

**Purity REST facts the hardware taught:** /audits rejects a filter on `time` ("Unknown attribute"), so the cursor is applied locally to the newest audit_batch records sorted by time; /alerts/events on REST 2.46 answers "Must specify an alert ID(s)" (needs 2.50), so the alerts signal diffs /alerts with state != closed and derives opened / updated / closing / closed itself; history resolutions are fixed at 30 s, 5 min, 30 min, 2 h, 8 h, 1 day, anything else is "Invalid resolution"; maintenance windows accept 3600 to 172800 seconds, not minutes; GET /alert-watchers/test needs explicit watcher names; a protection group's targets are not on the group object at REST 2.46 (/protection-groups/targets is one extra call per poll); transfers that completed before the poller started have no `started`, so the drill picks the latest `completed`; Purity logs NTP changes as `purearray setattr --ntpserver` (there is no purentp command) and DNS changes as `puredns setattr`, so a rule written from the CLI manual rather than the audit log would never have fired.

**Collection and SDK facts:** SDK models raise AttributeError for fields the array did not return (volume.qos.iops_limit on an uncapped volume), use to_dict(); purefa_pgsnap forbids `now` together with `remote`, and `remote: true` alone is the immediate replicated snapshot; connections to a stretched pod's volumes list the peer array's hosts as `<array>:<host>`, only unqualified names are local and changeable; host.preferred_arrays comes back as references; purefa_volume takes iops_qos: 0 to clear a limit and rejects the array's own "no limit" value 100000000; volume and array performance samples are not simultaneous, so the IOPS share is clamped to 100 % (the recorded qos_cap.log line pre-dates the clamp).

**Design rules:**

- **Facts, not verdicts.** The plugin docstring: "Thresholds, baselines and policy live in the rulebook, not here." The thresholds behind the booleans are plugin arguments fed from the vars file; the comparisons against site policy (capacity_risk_pct, rpo_escalate_polls, hotspot_consecutive_polls) stay in the rulebook conditions.
- **State on the array or in a file.** The QoS cap is two volume tags in namespace eda that the telemetry signal reads back as eda_capped / eda_cap_since, so a restart loses nothing and an operator can see that the automation capped the volume, since when, and what limit it had before; the approval request is a JSON file with a status lifecycle awaiting_approval -> done; the desired configuration is a git repository, one <array>.yml per inventory host. The plan had proposed set_fact / retract_fact; the build replaced it. Deliberately in-process only, lost on restart and recomputed within a few polls: the alert seen-set (so the first poll after a restart emits `initial`, not false `opened`), the audit cursor, the last primary controller, the previous space sample and volume sizes, the high-latency and normal poll counters, RPO breach streaks, paused-since stamps, the set of degraded pods and the last transfer progress; none of them is a verdict.
- **A dedicated service account.** "Running the automation as a dedicated service account is not optional." (docs/PHASE1.md). Read-only token for the poller; a separate write credential named in automation_users.
- **Let the array hold the thresholds and the baseline.** Days-to-full from the array's own 7-day space history; write latency compared with the same half hour one week ago at 30-minute resolution; top-N volumes by server-side sort and limit without paging; alert thresholds the array already applies through /alerts/rules. Blog: "A Tuesday morning backup window stops looking like an incident."

## 10. Objections and honest answers

1. **"Isn't this monitoring with extra steps? We have Pure1 / Fusion / Prometheus."** The point is that the three primitives (alert stream, attributable audit log, history) are on the array itself, so the loop needs nothing else; if you already run Prometheus, the zero-custom-code path uses it with the stock Alertmanager source and the same playbooks. The predecessor needed Fusion; this removes that dependency rather than adding a stack.
2. **"What stops the automation doing damage?"** Only NTP and DNS auto-revert; LDAP, SafeMode/eradication and admin-auth are notify-only ("an automation account that can loosen them is itself the risk"); anything that frees space needs an approval and SafeMode-locked objects are refused by the array, not forced; the anomaly response only adds protection; every remediation is suppressed inside a maintenance window; replication and QoS actions sit behind per-site switches that fall back to notify; the poller's token can carry a read-only role (the plugin only issues GETs). Observed: the approval path eradicated one scratch volume and reported the locked snapshot as refused.
3. **"Has this run in production?"** No. All five phases ran once against two lab arrays on 2026-10-20, about 53 minutes of recorded runs. Prototype, not a product, not supported by Everpure or Red Hat.
4. **"You cannot have tested a drive or controller failure."** Correct. Hardware failures and real degradation were replayed from recorded fixtures through the generic source; the actions were real: the LED on CT1 lit and was cleared, preferred arrays really moved and were restored, the overdue rule really took a replicated snapshot.
5. **"Does the push path work with a real array?"** Not yet shown. The lab arrays cannot reach the EDA host; the listener was exercised with replayed lines over UDP and TCP, the parser follows the layout published by Pure's SIEM partners, and "the first real line may need a regex adjustment". Likewise the Prometheus rules were not evaluated against a live Prometheus and the decision environment image has not been built.
6. **"Does an AAP approval node pause a workflow launched from a rulebook?"** Unproven. The prototype's approval gate is a webhook ruleset standing in for the workflow node; the plan flagged the AAP 2.5 behaviour as not stated in the docs read.
7. **"Our arrays are older than 6.10."** The lab itself was REST 2.46, below the 2.50 floor for /alerts/events, so the shipped alerts signal already uses the fallback (diff /alerts, REST 2.0). The OpenMetrics path needs Purity//FA 6.7+; other endpoints used are REST 2.0 to 2.52.
8. **"Thresholds are always wrong for someone; this will page us for a backup window."** That is the argument for letting the array hold thresholds and comparing now with the same half hour last week (baseline_latency_ratio 3x); counters need N consecutive polls (hotspot_consecutive_polls 3); the composite rule needs three independent signals plus a human destructive command inside 15 minutes, throttled to once an hour per array. Honest limit: the lab was idle, so QoS and anomaly rules were exercised with lowered thresholds and replayed signals, not a real backup window.
9. **"What if someone else uses the automation account?"** It happened: a QA harness shared the account and its changes were indistinguishable from an operator's until automation_users named the account. A dedicated service account is not optional; its own changes are logged, never reconciled.
10. **"Where are ServiceNow, Slack and the host-side checks?"** Not in the repository. notify and ticket append a JSON record to an alert log file and print it; the anomaly rule's "page" is protect_now.yml's critical record in that log; the playbooks mark where servicenow.itsm.incident, jira, mail or Slack would go. Host-side multipath, vSphere, Cinder and remote-assist actions are plan and blog content, not code.
11. **"Does the DR drill prove the copy is mountable?"** Not in the built version. It copies one member volume out of the latest completed transfer on the target, verifies the copy exists at the expected size, then destroys and eradicates it; a missing completed snapshot or a failed copy records a failure. The plan's "mount and verify from a test host" was not implemented; say "copies and size-verifies".
12. **"How does the anomaly rule avoid making a ransomware event worse?"** The response is additive only: an immediate snapshot of every local protection group (a clean recovery point from before the rule fired), a longer eradication delay (the direction SafeMode allows), a critical record (the rule's "page"). Observed: the enabled delay went from 1 to 2 days and the snapshot in a SafeMode-protected group could not be eradicated afterwards, as designed.
13. **"How fast is it really?"** Pull latency is the poll interval: audits every 10 s in the lab (the NTP revert landed within one poll), alerts 15 s, telemetry 15 to 20 s; example production values are audits 15 to 60 s, alerts 60 s, health 300 s, telemetry 60 to 300 s, replication 60 s, config 300 to 900 s. Push is sub-second but not yet shown against a live array. No end-to-end figure beyond "within one poll" exists.
14. **"How many arrays can one instance handle?"** Unknown; two in the lab. Design intent: one plugin, N arrays, one reused client per array, per-signal intervals, SDK calls in a thread pool. Untested.
15. **"Is this certified / on Automation Hub?"** No. Packaging into everpure.flasharray and the Red Hat EDA certification track were the Phase 4 goal and are not started; the layout already matches the collection's extensions/eda shape, and the remaining work is naming, documentation blocks and Red Hat's tests.

## 12. Glossary

- **FlashArray / Purity//FA**: Everpure's block and file storage array and its operating environment; the lab ran Purity//FA 6.10.6. **REST 2.46 / 2.50**: versions of the array's REST API; some endpoints exist only from a given version.
- **py-pure-client**: the Python SDK for the array's REST API (1.94.1 here). **everpure.flasharray**: the Ansible collection of FlashArray modules (purefa_ntp, purefa_host, purefa_pgsnap and so on); 1.46.0 or later.
- **Event-Driven Ansible (EDA) / ansible-rulebook**: the Ansible component that listens to event sources, evaluates rule conditions and runs playbooks; the rule engine underneath is Drools. **EDA Controller / Ansible Automation Platform (AAP)**: Red Hat's managed form, where a rulebook runs as an activation inside a container image called a decision environment, and a workflow can pause at an approval node until a human approves.
- **Source plugin**: Python code that turns something (REST polls, syslog lines, webhooks) into events for a rulebook. **Rulebook / ruleset / rule**: a YAML file of rule groups, each rule a condition and an action. **Throttle (once_within)**: a per-rule cooldown so a condition fires at most once per window per group of attributes.
- **Alert**: a condition the array has raised itself, with a numeric code, severity, the component, the array's recommended action text and a knowledge-base link. **Audit record**: the array's log of every command run, with the user, interface, command, subcommand and arguments.
- **Baseline / drift / reconcile**: the desired configuration kept in git (one file per array); a difference from it; reapplying it. **Change control** here means reacting to the audit record of a change rather than to a later comparison.
- **Maintenance window**: a declared period (3600 to 172800 seconds) during which someone expects to be working on the array; this project uses it as the suppression signal.
- **Identify LED**: the locator light on a hardware component. **Controller (CT0 / CT1)**: the two controllers of an array; one is primary, and a failover swaps roles.
- **Replication terms**: array connection (the link between two arrays); pod (a container of volumes); pod replica link (asynchronous replication of a pod to a peer); stretched pod / ActiveCluster (a pod active on two arrays at once, with a mediator to break ties); protection group (a set of volumes snapshotted and replicated together on a schedule); transfer (one replicated snapshot moving to the target); recovery point (the age of the last replicated state); RPO (recovery point objective, the maximum tolerated age); preferred array (a per-host setting that drives which array's paths the host prefers, via ALUA).
- **DR drill**: proving a replicated copy is usable; here, copying one volume out of the latest completed replicated snapshot on the target and checking its size.
- **Capacity terms**: data reduction ratio (DRR, how much smaller data is stored than written; a sudden drop is one ransomware indicator); days to full (projected from recent growth); pending eradication (destroyed objects still recoverable until a timer runs out); eradication delay (that timer, in days). **SafeMode**: the array's retention lock: destroyed objects cannot be eradicated before the delay runs out, and in this project automation only ever lengthens the delay and only ever notifies on SafeMode settings.
- **QoS / IOPS limit**: a per-volume cap on I/O operations per second; the array stores "no limit" as 100000000. **Noisy neighbour**: one volume degrading others on a busy array. **Hysteresis**: applying a change at one condition and reversing it only after a different, calmer condition has held for a while.
- **Syslog, purity.alert / purity.audit / purity.test**: the array's log-forwarding channel and the three program names it uses. **OpenMetrics exporter / Prometheus / Alertmanager**: the array's native metrics endpoint (Purity//FA 6.7+), the scraper that stores metrics and evaluates rules, and the component that routes resulting alerts, here by webhook into EDA.
- **Idempotent**: an action that can be repeated without changing the result after the first time; reapplying the NTP baseline is idempotent.
- **Cinder / OpenStack**: the OpenStack block-storage service; a Cinder host appeared in the lab as a consumer of a stretched-pod volume. **Fusion / Pure1**: Everpure's fleet-management control plane and cloud management service; the predecessor project depended on Fusion.
